# ADM-001.1 — Painel de administração central

## Escopo desta etapa

O painel central tem identidade e navegação próprias e é acessado localmente em `http://127.0.0.1:5173/admin`. A rota da interface só é incluída em desenvolvimento. A API administrativa roda em um processo Express separado, na porta local 3002, ligado apenas a `127.0.0.1`.

A autenticação não consulta contas das oficinas. O painel usa o cookie `hp_platform_session`, exige senha e TOTP e mantém seus usuários, sessões e auditoria no schema PostgreSQL `platform_admin`. O processo usa o papel `hp_platform_admin_app`, que não tem `USAGE` nos schemas `horse_power` e `service_catalog`. O backend operacional continua usando `hp_local_app` e `hp_session`.

Os perfis são Administrador principal, Financeiro, Suporte técnico e Comercial. O principal é o único que cria, desativa e altera contas. Cada conta não principal recebe somente as permissões escolhidas explicitamente. O servidor valida cada operação. O principal não pode alterar a própria conta; uma conta não pode desativar o último principal ativo.

O convite de conta é um token aleatório gerado no navegador e armazenado somente como hash, válido por 30 minutos e de uso único. A pessoa convidada cria sua própria senha e configura TOTP antes de ativar a conta. O link é exibido uma vez e usa fragmento (`#invite=...`), que não é enviado no pedido inicial ao servidor. O token e o segredo TOTP não são devolvidos nos corpos das respostas da API; o segredo TOTP é gerado no navegador durante a ativação e enviado no pedido para armazenamento cifrado. Não existe recuperação que ignore o segundo fator nesta etapa.

A auditoria registra autenticação, falhas de senha/TOTP, login, logout, convites, alterações de permissões e estado de contas. Eventos são somente leitura para o papel da aplicação e possuem trigger que rejeita alteração e exclusão. A configuração guarda retenção de 365 dias; não há rotina de expurgo. A tabela de aprovação crítica impede aprovação pelo solicitante e não tem endpoint de aprovação implementado.

## Preparação local

Execute uma vez, no terminal do projeto, após conferir que `.env.local` aponta para `horse_power_local` em loopback:

```powershell
npm.cmd run db:local:migrate
```

O script confirma os checksums das migrações antigas e aplica apenas a nova migração `004-platform-admin.sql`. Ele provisiona o papel de banco restrito, gera uma senha aleatória para essa conexão e uma chave para cifrar segredos TOTP. Os valores são gravados em `.env.platform-admin.local`, arquivo ignorado pelo Git; não os copie para o repositório. Se o papel já existir sem sua configuração correspondente, o script para sem trocar credenciais.

Configure a primeira conta principal em terminal interativo:

```powershell
npm.cmd run admin:bootstrap
```

O comando pede e-mail, nome e senha (entrada mascarada). Exibe o segredo TOTP uma única vez no terminal para cadastro manual no aplicativo autenticador e pede o código atual antes de gravar a conta. Uma senha com pelo menos 14 caracteres é obrigatória. O comando não reutiliza usuários das oficinas e recusa uma segunda execução quando já existe qualquer conta administrativa.

### Conta fictícia para desenvolvimento local

Para desenvolver sem cadastrar uma identidade pessoal, use o comando separado:

```powershell
npm.cmd run admin:seed:local
```

Ele cria `admin@plataforma.local` com perfil principal e MFA ativo, usando somente `PLATFORM_ADMIN_DATABASE_URL` configurada para o banco `horse_power_local` em `127.0.0.1` ou `localhost`. O processo também confirma o banco, o endereço loopback e o papel restrito após conectar. Ele recusa execução sob Vercel, produção ou homologação e não lê `DATABASE_URL`, URLs Supabase nem credenciais do painel das oficinas. A conta administrativa continua sem acesso aos schemas operacionais.

A senha aleatória e o segredo TOTP ficam em `.platform-admin-local.json`, ignorado pelo Git. No Windows, o comando remove as permissões herdadas e concede acesso somente à conta atual do Windows; em outros sistemas usa modo `0600`. Para consultar a senha localmente, abra esse arquivo no Bloco de Notas, sem copiá-lo para o repositório ou compartilhá-lo. Para ver o código TOTP atual no terminal, execute:

```powershell
npm.cmd run admin:totp:local
```

Use e-mail e senha do arquivo, mais o código recém-exibido, no fluxo normal em `http://127.0.0.1:5173/admin`. Inicie também `npm.cmd run dev:admin` em outro terminal. A consulta TOTP só funciona se o arquivo corresponder à conta ativa no banco local; não existe rota HTTP para consultar credenciais.

O comando de preparação pode ser repetido: se o e-mail reservado já existir, ele não troca senha nem MFA e não duplica a conta. Se a conta estiver ativa, inscrita no MFA e ainda tiver papel `principal`, o comando acrescenta idempotentemente apenas `workshops:read` e `workshops:manage`, preservando as demais permissões, sessões e histórico e registrando uma única auditoria. Contas inativas, sem MFA concluído ou com outro papel não são atualizadas. A auditoria da criação é registrada somente quando a conta é criada. Para remover esta identidade no futuro, use o painel local para desativá-la; não recrie o banco para esse fim.

Para iniciar o ambiente, use dois terminais na pasta do projeto:

```powershell
npm.cmd run dev
```

```powershell
npm.cmd run dev:admin
```

Abra `http://127.0.0.1:5173/admin`. Envie convites pela aba Administradores e entregue o link exibido diretamente à pessoa convidada. O sistema não envia e-mail.

## Migração e proteção dos dados

`local-postgres/004-platform-admin.sql` cria schema, tabelas, índices, função e trigger administrativos; configura grants no schema novo e revoga qualquer acesso administrativo aos schemas operacionais. `005-platform-admin-connect.sql` concede `CONNECT` ao papel em `horse_power_local`. `006-platform-admin-constraints.sql` reforça no banco a exigência de MFA antes de ativar uma conta e limita as permissões aos valores conhecidos; `007-platform-workshops.sql` amplia a allowlist para as permissões de gestão de oficinas sem conceder acesso do papel administrativo às tabelas operacionais. As migrações não alteram, copiam ou removem oficinas, clientes, documentos ou dados financeiros e ficam registradas com checksum em `local_setup.migrations`.

O segredo TOTP fica cifrado com AES-256-GCM. O papel da aplicação não pode criar schemas, papéis ou bancos e não acessa as tabelas operacionais. As rotas do painel não recebem a conexão `hp_local_app`. O serviço recusa iniciar sob Vercel/produção e escuta somente em loopback.

## Testes e validação

```powershell
npm.cmd run build
npm.cmd test
npm.cmd run test:postgres
```

Os testes PostgreSQL criam um schema temporário com prefixo `platform_admin_test_`, usam somente contas fictícias e o removem ao terminar. Eles verificam autenticação, segundo fator, separação de cookies, perfis, auditoria, convites de uso único, bloqueio após desativação e negação de leitura dos schemas operacionais. O teste depende da migração local aplicada e da configuração `.env.platform-admin.local`.

## Limites e riscos pendentes

- Os módulos de oficinas, planos, assinaturas, cobranças, catálogo, monitoramento e suporte aparecem apenas como planejados.
- A aprovação de operações críticas tem estrutura de dados, mas nenhuma operação sensível ou fluxo de aprovação foi habilitado.
- A entrega do convite é manual. O token deixa de ser mostrado após fechar a tela e pode ser renovado por um principal enquanto a conta não foi ativada.
- Não há recuperação automática do TOTP. A chave de cifragem e a conexão administrativa ficam em arquivo local ignorado pelo Git; proteja a pasta com a conta do Windows e mantenha um plano de recuperação local antes de depender do painel.
- A retenção de auditoria está configurada para 365 dias, mas os registros não são excluídos automaticamente. Qualquer política futura deve ser explícita e auditável.
- A configuração é apenas para desenvolvimento local. Um futuro domínio administrativo exige implantação, segredos e revisão de infraestrutura próprios; esta etapa não altera hospedagem nem configura domínio.
